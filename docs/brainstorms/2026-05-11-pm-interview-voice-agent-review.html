★ The three big premise concerns

Three premise-level concerns surfaced from independent personas converging — these are likely worth resolving before planning:

1. Audience-fit across three different employers

Sarvam = Bharat/Indic voice; ElevenLabs = audio quality/creator-tool; Wispr Flow = input-method ergonomics. A Google-Meta-persona English PM simulator is closest to ElevenLabs, neutral-to-weak for Sarvam, tangential for Wispr Flow. Product-lens raised this 4 different ways.

2. BYO-key adoption tax vs ~100-user target

PM candidates are not the developer audience — most don't have provider keys. Against free ChatGPT voice mode, the BYO friction is a real adoption tax. Product, design, adversarial, and security personas all touch this.

3. V1 scope ambition vs stated "deep, not broad" discipline

Homepage richness (R2-R4), provider abstraction (R16), and the V0 bakeoff publication (R18) are all bigger than "one case, deep" suggests. Scope-guardian + product-lens converge here.

Most other P0/P1 findings are gated_auto with concrete fixes — the doc is missing things rather than wrong about things, which is a good sign for a brainstorm-tier artifact.

P0.1 P0 design-lens omission recommended: Apply
Voice error states entirely absent from requirements
Session UI (three-panel layout)
What's wrong

R9 specifies only three agent states (listening, thinking, speaking). Implementers will inevitably hit mic-permission-denied, network drop mid-session, ASR returning no result, API key invalid/expired, and provider timeout — without specified states for each, every implementer will invent different error UX. A candidate mid-session who sees no feedback has their session ruined with no recovery path, undermining the product's core value.

Proposed fix

Add a requirement enumerating 5 error states with orb animation behavior, status dot color, status text copy, and recovery action each: (1) mic-permission-denied with grant-permission affordance, (2) network-drop with reconnecting status, (3) ASR-no-result with prompt to repeat, (4) API-key-invalid with full-panel error pointing back to onboarding, (5) provider-timeout with retry affordance.

P0.2 P0 design-lens omission recommended: Apply
Onboarding step has no error or validation states
Onboarding & access (V1)
What's wrong

R6 describes key entry and persistence but says nothing about what happens when a key is wrong, malformed, or rejected by the provider on first use. An invalid Anthropic key isn't caught until the first LLM call fires after case selection — leaving the candidate inside the session screen with a broken AI and no specified recovery path. Implementers will silently swallow the failure differently.

Proposed fix

Validate keys synchronously at end of onboarding via lightweight test call to each provider before the session screen renders. Show inline field validation for format (e.g., sk- prefix check), provider-specific error copy ("Invalid Anthropic key — check at console.anthropic.com"), and a clear re-entry path. Gate session start on successful ping response.

P1.7 P1 adversarial error recommended: Apply
ASR mishearing has no recovery for accented speech
Session UI + Acceptance Examples
What's wrong

R11 explicitly excludes inline edit; AE4 prescribes re-speaking. For a candidate (including the operator) speaking accented English, 15-30% ASR error rates on PM-jargon-heavy speech ("user research," "north-star metric," "CIRCLES") are realistic. Re-speak compounds: each correction adds another listen-think-speak cycle, the mis-captured line still stands (R11), and the interviewer LLM reads the wrong transcript as context — so the AI's next probe may be answering the mis-captured version. Degrades framework-aware probe quality (R13) silently.

Proposed fix

Instrument per-session ASR confidence/re-speak rate so "demand for edit" is measurable, not felt. Alternatively, soften R11: V1 supports striking through a mis-captured line so the LLM context excludes it, even without full inline edit. Add an AE covering accented-speech ASR consistently below a threshold.

P1.13 P1 security-lens omission recommended: Apply
BYO keys in browser with no XSS mitigation
Onboarding & access (V1) / AE3
What's wrong

API keys persisted in localStorage (the natural implementation of AE3's "still available locally after reload") are trivially exfiltrated by any XSS vector — a malicious third-party script, an injected ad, or a supply-chain attack on a dependency. The candidate's LLM and voice provider keys would be stolen silently. Single-page voice app likely pulls several npm packages and potentially an embedded video — non-trivial attack surface. Doc defers the cryptographic posture entirely to planning.

Proposed fix

Resolve storage now: (1) prefer sessionStorage over localStorage to limit persistence to tab lifetime; (2) if cross-reload is required (R6), document threat-accepted decision and add CSP header blocking inline scripts + restricting script-src to a known allowlist; (3) client-side encryption offers marginal benefit if the key is also in JS — the real mitigation is CSP + subresource integrity on dependencies.

P1.14 P1 security-lens omission recommended: Apply
Private operator frameworks: no access control defined
Framework awareness (V1) / F4
What's wrong

R20 says private frameworks load via "non-public mechanism" but specifies no concrete access control. The deferred question lists env-var, hidden route, and local-only build flag — none of which enforce authentication. A hidden route is security-through-obscurity: URL enumeration, client bundle analysis, or a public source repo would expose it. An env-var works only if never bundled into client-side JS. Implementer will likely pick whichever is easiest, which may be client-accessible.

Proposed fix

Specify the mechanism must enforce server-side access control, not rely on obscurity alone. Acceptable patterns: (a) private frameworks live in server-side env-var injected only at server-render time and never in client JS bundle; (b) a route requiring pre-shared secret as a header (not URL parameter), with the secret never committed to source control.

P1.16 P1 adversarial omission recommended: Apply

Session UI + Voice integration
What's wrong
